# Сопровождение job-market-analyzer

CLI-инструмент на Python (typer) для соискателя BA/SA: вакансии с HH.ru → анализ навыков → письма и советы по резюме через LLM. Пользователь — аналитик и владелец продукта: решения о требованиях, приёмке и публикации принимает он; код и проверки — твоя часть.

Если передан аргумент (`$ARGUMENTS`), начни с соответствующего раздела; иначе выбери разделы по задаче.

## 1. Ориентация (orient)

Изменчивые факты (статусы US, данные, бэклог, следующий шаг) в этом скилле не дублируются — читай их из источников:

1. `docs/STATUS.md` — состояние проекта, ключевые решения, следующий шаг. Читать первым.
2. `requirements.md` — US и AC (раздел 4), NFR (5), структура (6), CLI (7), открытые вопросы (8), **бэклог (9)**.
3. Нужный модуль `src/` и глава `docs/user-guide/` по команде.

| Модуль | Отвечает за |
|---|---|
| `src/cli.py` | Команды typer, переопределение настроек опциями, UTF-8 вывод |
| `src/config.py` | Загрузка `profile/preferences.json` (US-01), `PROJECT_ROOT` |
| `src/hh_client.py` | HH API через внешний curl, выгрузки `data/raw_vacancies_*.json`, кэш описаний `data/details/` (US-02) |
| `src/analyzer.py` | Навыки по словарю + LLM вне словаря, Gap Analysis с резюме (US-03) |
| `src/cover_letter.py` | Письмо под вакансию, общие загрузка промпта и выбор языка (US-04) |
| `src/cv_tips.py` | Советы по резюме с проверками кодом (US-05) |
| `src/llm_service.py` | Единая точка `ask_json()`: Claude API и OpenAI-совместимые провайдеры (ADR-001) |
| `src/text_utils.py` | Формы слов, сверка цитат LLM с исходным текстом |
| `scripts/eval_cover_letters.py` | Прогон писем набора приёмки на любой модели → `reports/eval/` |
| `prompts/*.md` | Промпты LLM; `prompts/experiments/` — отклонённые варианты |

Не в git (личное и генерируемое): `.env`, `profile/my_cv.md`, `data/*`, `reports/*` (кроме `.gitkeep`), `tmp/`, `.obsidian/`, `.venv/`. Не предполагай файлы, которых нет, — проверяй.

## 2. Запуск (run)

Из корня проекта, PowerShell:

```powershell
.venv\Scripts\python.exe -m src.cli --help
.venv\Scripts\python.exe -m src.cli fetch --region 16
.venv\Scripts\python.exe -m src.cli analyze --area Минск
.venv\Scripts\python.exe -m src.cli cover-letter <id>
.venv\Scripts\python.exe -m src.cli cv-tips <id>
```

В bash (и через `!` в Claude Code) — прямые слэши: `.venv/Scripts/python.exe -m src.cli ...`. Не вызывай голый `python` — он может зависнуть (заглушка Microsoft Store) или оказаться без зависимостей.

| Команда | Сеть | Стоимость | Что перезаписывает |
|---|---|---|---|
| `--help`, `<команда> --help` | нет | бесплатно | ничего |
| `fetch` | HH через curl | бесплатно, но лимиты HH | добавляет выгрузку и описания в `data/` |
| `analyze --no-llm` | нет | бесплатно | `reports/market_skills_summary.md` |
| `analyze` | LLM | ~1 цент | отчёт и кэши LLM в `data/` |
| `cover-letter`, `cv-tips` | HH (если нет в кэше) + LLM | $0,01–0,07 | ничего — новые версии файлов `_v2`, `_v3` |

**Правило:** любой запуск, который тратит деньги, ходит в HH или перезаписывает отчёт пользователя, — только после его согласия. Если команду запускает пользователь сам — дай пошаговую инструкцию с ожидаемым результатом.

Окружение и известные ловушки:
- Ключи — в `.env` (образец `.env.example`). Никогда не выводи значения ключей в чат и не читай `.env` без нужды; для проверки наличия достаточно имени переменной.
- Пользователь работает через Mullvad VPN: HH доступен только через curl, исключённый из VPN (`HH_CURL_PATH`). Не переводи запросы к HH на `requests`/WebFetch и не предлагай исключать Python из VPN — Claude API работает только через VPN.
- Кириллицу в параметрах URL для curl кодировать в Python (`urlencode`) заранее.
- Вывод CLI принудительно в UTF-8 (`main()` в `cli.py`, Q15) — не убирай: иначе вне консоли кириллица искажается, а на «→» команда падает.
- Если auto-режим не может проверить команду — предложи пользователю выполнить её через `!` или в обычном режиме разрешений.

## 3. Внесение изменений (change)

1. Найди основание в `requirements.md`: какая US/AC/NFR или пункт бэклога. Нет основания — это новое требование: предложи уточнить его (например, через скилл `requirements-interview`) до кода.
2. Объясни подход и покажи план — жди подтверждения.
3. Делай **один шаг**: после него проверка (раздел 4) и совместная проверка с пользователем. Следующий шаг — только после подтверждения.
4. Подтверждённый шаг — отдельный коммит (сообщение на английском, как в истории) и push. Перед коммитом — `git status` и `git diff --cached --stat`: в индексе не должно быть файлов из списка «не в git».
5. Исправления дефектов и замечаний — по одному, каждое после обсуждения.

Соглашения кода:
- Пиши как окружающий код: докстринги и комментарии на русском, ссылки на AC/US/ADR/Q/бэклог в комментариях там, где решение из них следует.
- LLM вызывается только через `llm_service.ask_json()`; провайдер и модель — из `llm_preferences.llm_providers` в профиле, не хардкодить.
- Промпты — в `prompts/`, не в коде. Эксперименты с промптом — по одной переменной, через `scripts/eval_cover_letters.py`; отклонённые варианты сохраняются в `prompts/experiments/`.
- Ответы LLM проверяются кодом (цитаты — с резюме, термины — со словарём, числа — с резюме), неподтверждённое помечается ⚠️. Новая генерация без такой проверки — повод спросить пользователя.
- Новые настройки — в `profile/preferences.json` с описанием в `docs/user-guide/configuration.md`.
- Архитектурный выбор с альтернативами — новый ADR в `docs/adr/` (формат — по существующим).
- Отложенное в обсуждении — сразу в бэклог, раздел 9 `requirements.md`.

## 4. Проверка ошибок (check)

Автотестов и линтера в проекте нет. Бесплатные проверки — выполнять сам после каждого изменения кода:

```bash
.venv/Scripts/python.exe -m compileall -q src scripts
.venv/Scripts/python.exe -c "import src.cli"
.venv/Scripts/python.exe -m src.cli --help
for c in fetch analyze cover-letter cv-tips; do .venv/Scripts/python.exe -m src.cli $c --help > /dev/null || echo "FAIL: $c"; done
.venv/Scripts/python.exe -c "import json; json.load(open('profile/preferences.json', encoding='utf-8'))"
```

Дальше — по согласию пользователя, от дешёвого к дорогому: `analyze --no-llm` (перезапишет отчёт) → одна LLM-команда на вакансии из кэша `data/details/` → `fetch`.

При разборе ошибки: сначала `docs/user-guide/troubleshooting.md` и ловушки из раздела 2, затем код. Если ошибка — дефект по AC, предложи записать его в протокол приёмки `docs/testing/` или в бэклог.

Итог проверки сообщай как есть: что запускалось, что прошло, что упало (с выводом), что не проверялось.

## 5. README и документация (docs)

Что обновлять после изменения:

| Изменилось | Обновить |
|---|---|
| Поведение или параметры команды | `docs/user-guide/<команда>.md`, при необходимости `requirements.md` раздел 7 |
| Настройки профиля | `docs/user-guide/configuration.md` |
| Новая ошибка или обход | `docs/user-guide/troubleshooting.md` |
| Стоимость, модели | `docs/user-guide/costs.md`, ADR-001 при смене решения |
| Статус US, решения, данные, следующий шаг | `docs/STATUS.md` (дата в frontmatter и «Обновлено», последний коммит) |
| Возможности, результаты, артефакты | `README.md` |

**README — витрина портфолио**, а не техническая справка. Структура: задача → что умеет (таблица с US) → результаты (цифры) → артефакты аналитика (таблица ссылок) → как велась разработка → запуск и структура со ссылками на руководство. Роль пользователя — аналитик и владелец продукта, код написан Claude Code — формулировку не менять без его согласия. Цифры в README брать из `STATUS.md` и протоколов, не придумывать. Mermaid-диаграммы допустимы (GitHub их рендерит).

Правила документации:
- У команды: сначала синтаксис, затем расшифровка каждого параметра (значения, где взять, значение по умолчанию), затем примеры.
- Термины проекта определяются при первом упоминании; общий словарь — «Основные термины» в `docs/user-guide/index.md`.
- Формат под Obsidian и GitHub одновременно: относительные ссылки `[текст](путь.md)`, без `[[wikilinks]]` в файлах, которые читают на GitHub. Callout-блоки и `[[#ссылки]]` — только в генерируемых отчётах.
- Без личных данных из резюме в файлах под git.
