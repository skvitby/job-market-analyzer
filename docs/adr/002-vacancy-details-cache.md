# ADR-002: Хранение полных описаний вакансий в отдельном кэше `data/details/`

**Статус:** Принято
**Дата:** 29.09.2026 (решение принято на шаге 5 реализации US-02, оформлено ретроспективно перед US-04)
**Связанные требования:** US-02 (AC 2.4, AC 2.7), US-03 (AC 3.1), US-04 (AC 4.1), US-05 (AC 5.1), NFR-1, открытый вопрос №4

## 1. Контекст

`fetch` сохраняет результаты поиска HH в снимки `data/raw_vacancies_{timestamp}.json` с полями из AC 2.4. Поиск `GET /vacancies` не отдаёт полное описание вакансии и `key_skills`, только сниппеты `requirement` / `responsibility`. Они занимают около 330 символов и часто обрезаны. Для Gap-анализа (US-03) этого мало, а для сопроводительного письма и советов по резюме (US-04, US-05) нужен полный текст.

Полное описание можно получить только отдельным запросом `GET /vacancies/{id}` на каждую вакансию.

**Ограничения:**
- **Rate limit HH:** пауза 3 сек между запросами (NFR-1). Первая загрузка ~900 вакансий занимает около 45 минут.
- **Снимки пересекаются:** выгрузки инкрементальные, по регионам, и одна вакансия может попасть в несколько файлов `raw_vacancies_*`.
- **Нестабильная сеть:** запросы к HH идут через curl вне VPN, поэтому долгая загрузка может оборваться: сбой сети, 429/503, Ctrl+C.
- **Полный текст нужен нескольким модулям:** `analyze` (US-03), `cover-letter` (US-04), `cv-tips` (US-05).

## 2. Критерии выбора

1. **Время загрузки** — описание каждой вакансии запрашивается у HH не больше одного раза.
2. **Устойчивость к сбоям** — прерванная загрузка продолжается без потери уже скачанного.
3. **Отсутствие дублирования** — одно описание хранится в одном месте.
4. **Простота доступа** — любой модуль получает полный текст по `id`.
5. **Неизменность снимков** — файл выгрузки отражает результат конкретного поиска и не меняется задним числом.
6. **Простота реализации** — без новых зависимостей и инфраструктуры.

## 3. Рассмотренные варианты

### 3.1. Описание внутри снимков `raw_vacancies_*.json`

После поиска догрузить описания и записать их в тот же файл выгрузки.

- ➕ Все данные о вакансии в одном месте, склейка не нужна.
- ➖ Одна вакансия в нескольких снимках: описание либо дублируется, либо его приходится искать по старым файлам.
- ➖ Узнать, что уже загружено, можно только чтением всех снимков.
- ➖ Большой JSON нужно перезаписывать целиком, поэтому при обрыве на 40-й минуте результат теряется или файл повреждается. Частичное сохранение потребовало бы отдельной логики.
- ➖ При `fetch --no-details` снимок пришлось бы дописывать задним числом.

### 3.2. Загрузка описаний «по требованию» в `analyze`

Не хранить описания, а запрашивать их у HH при каждом анализе.

- ➕ Не нужно хранилище.
- ➖ Каждый запуск `analyze` занимает десятки минут.
- ➖ Анализ зависит от доступности HH и VPN-обхода, работать офлайн нельзя.
- ➖ Работа с HH оказывается в модуле анализа, и границы модулей из раздела 3 ТЗ смешиваются.

### 3.3. Единое хранилище: SQLite или один файл `details.json`

- ➕ Одна точка доступа, возможны запросы и индексы.
- ➖ SQLite — новая технология в проекте, данные нельзя просто открыть и посмотреть в редакторе или Obsidian.
- ➖ Один JSON-файл имеет те же проблемы с перезаписью и обрывами, что и вариант 3.1.
- ➖ На объёме проекта (тысячи вакансий) выигрыш не оправдывает усложнения.

### 3.4. Отдельный кэш: файл на вакансию `data/details/{id}.json` ✅

Снимки поиска остаются как есть. Полное описание и `key_skills` каждой вакансии хранятся в отдельном файле с именем по `id`.

- ➕ Каждое описание загружается один раз. Список загруженных вакансий — это просто список файлов в папке.
- ➕ Каждое описание сохраняется сразу после загрузки: через временный файл с атомарной заменой. После обрыва скачанное остаётся, следующий `fetch` догружает остальное.
- ➕ Нет дублирования: одно описание используется всеми снимками.
- ➕ Снимки не меняются. `fetch --no-details` быстро собирает список вакансий, описания можно догрузить позже.
- ➕ Все модули получают полный текст по `id` одинаково.
- ➖ Данные о вакансии лежат в двух местах (см. раздел 5).

## 4. Решение

Выбран **вариант 3.4**.

| Хранилище | Содержимое | Наполняет | Назначение |
|---|---|---|---|
| `data/raw_vacancies_{timestamp}.json` | Метаданные вакансий: `id`, `name`, `salary`, `area`, `employer`, сниппеты, `alternate_url`, `published_at` (AC 2.4) | `fetch`, поиск | Снимок результатов конкретного поиска |
| `data/details/{id}.json` | `id`, `description` (абзацы в Markdown), `key_skills`, `fetched_at` (AC 2.7) | `fetch`, догрузка по `id` | Полный текст вакансии для анализа и генерации |

**Правила:**
- Описания загружает модуль сбора (`hh_client.py`) в `fetch`. `analyze` работает только с локальными данными, офлайн.
- Уже загруженные `id` у HH повторно не запрашиваются.
- Ошибка загрузки одной вакансии не прерывает выгрузку. При следующем `fetch` загрузка этой вакансии повторяется.

## 5. Последствия

**Положительные:**
- Первая загрузка — около 45 минут, последующие — только новые вакансии.
- `analyze` работает быстро и не зависит от сети.
- Долгую загрузку можно безопасно прерывать.

**Отрицательные и что с ними делаем:**
- **Данные о вакансии разделены.** Метаданные (название, работодатель, ссылка) лежат только в снимках, полный текст — только в кэше. Модулям, которым нужно и то и другое (US-04, US-05), нужна общая функция: она склеивает данные по `id`, а если вакансии нет в кэше — запрашивает её у HH и сохраняет в кэш. Это закреплено в AC 4.1 и AC 5.1.
- **Описание в кэше может устареть:** работодатель может отредактировать вакансию после загрузки. На задачи проекта это почти не влияет. Дата загрузки хранится в `fetched_at`, при необходимости по ней можно обновлять описания.
- **Кэш со временем растёт**, в нём копятся описания закрытых вакансий. Файлы небольшие, в среднем около 6 КБ (максимум 12 КБ), поэтому очистка пока не нужна.
- **Кэш не в git** (`data/*` в `.gitignore`). На другом компьютере его нужно собирать заново через `fetch`.
