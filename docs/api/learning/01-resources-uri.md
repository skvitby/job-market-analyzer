# Понятие 1. Ресурс и URI

Учебный шаг проекта REST API для US-06 (бэклог, п. 30): экран прототипа → понятие → проект API экрана → разбор.

## Теория

**Ресурс** — это «вещь», данные о которой отдаёт API: вакансия, выгрузка, письмо. В REST API строится вокруг ресурсов, а не вокруг действий. Это главное отличие от подхода «вызвать функцию».

**URI** — адрес ресурса.

### Правила

1. **Существительные, а не глаголы.** Действие задаёт HTTP-метод (о методах — в следующем понятии), а не адрес.
   - ✅ `/vacancies`
   - ❌ `/getVacancies`, `/loadVacancyList`
2. **Коллекция и элемент.** Коллекция называется во множественном числе, элемент — по идентификатору внутри неё.
   - `/vacancies` — все вакансии
   - `/vacancies/137828745` — одна вакансия
3. **Вложенность — для ресурсов, которые живут внутри другого.**
   - `/vacancies/137828745/cover-letters` — письма этой вакансии
   - Глубже двух-трёх уровней обычно не уходят.
4. **Фильтры, поиск, сортировка — в параметрах запроса (query), а не в пути.** Это та же коллекция, только с условием.
   - ✅ `/vacancies?is_new=true&search=аналитик`
   - ❌ `/vacancies/new`, `/vacancies/search/аналитик`
5. **Оформление:** строчные буквы, слова через дефис (`cover-letters`), без расширений (`.json`) и без слэша в конце.

> [!tip] Как запомнить
> Обычно путь хранит то, *что* это за ресурс, а query — *какую часть* коллекции показать.

## Разбор

> [!success] Итог
> Ресурсы найдены верно, схема «коллекция + элемент» применена правильно. Править — название выгрузок и устройство query-параметров.

### 1. Ресурсы — ✅ верно

Вакансии и выгрузки — именно те два ресурса, которые есть на экране.

Чего на экране **нет как отдельного ресурса**, хотя похоже:

- **Колонка «Подготовлено»** (есть письмо, есть советы) — это свойства вакансии в списке, а не отдельный ресурс. Сами письма и советы станут ресурсами на экране карточки: `/vacancies/{id}/cover-letters`.
- **Кнопки «Собрать вакансии» и «Анализ по этой выгрузке»** — это запуск команд, а не данные. Как в REST описывают действия, которые идут долго, разберём отдельным понятием.

### 2. URI — ✅ структура верная, ⚠️ название выгрузок

| Ваш вариант | Замечание | Как лучше |
|---|---|---|
| `vacancies`, `vacancies/{id}` | Верно. Мелочь: путь пишут со слэшем в начале | `/vacancies`, `/vacancies/{id}` |
| `unloadings`, `unloadings/{id}` | *Unloading* по-английски — разгрузка груза. Разработчик споткнётся о такое слово | `/fetches` — по имени команды `fetch`: один термин в CLI, коде и API. Другой вариант — `/exports`, но он звучит как «выгружаем от себя наружу» |

**Что считать `{id}`:**

- У вакансии — ID с hh (`137828745`). Он уже уникален и стабилен, придумывать свой не нужно.
- У выгрузки числового ID нет, есть файл `raw_vacancies_<дата-время>.json`. В роли `{id}` подойдёт метка времени из имени файла, например `/fetches/2026-10-02T18-44`. ID не обязан быть числом — он должен быть уникальным и не меняться.

> [!tip] Ubiquitous language
> Названия ресурсов берут из языка предметной области, одинаково во всех артефактах. У нас «выгрузка» в требованиях, `fetch` в CLI и `/fetches` в API — одно и то же понятие.

### 3. Query-параметры — ⚠️ главное место для доработки

Ваш вариант: `/vacancies?vac_filtr=all&search=`

| Что | Почему так не делают | Как лучше |
|---|---|---|
| `vac_` в имени | Параметр и так относится к `/vacancies`, приставка повторяет путь | Без приставки |
| `filtr` | Транслит, читается как опечатка | Английские слова или имя самого условия |
| Один параметр со значениями `all / new / letter / salary` | Условия независимы: «новые **и** с письмом» так не выразить. Кнопки «по одной» — решение интерфейса, API не должен им ограничиваться: завтра экран поменяется, а контракт останется | Отдельный параметр на каждое условие: `is_new=true`, `has_cover_letter=true`, `has_salary=true` — их можно комбинировать |
| `all` | «Все» — это отсутствие фильтра | Параметр просто не передают |
| `search=` пустой | Пустой параметр ничего не значит | Не передавать. Само имя `search` хорошее (часто пишут и `q`); в описании API указать, где ищем: название и работодатель |

Пример: «новые вакансии с зарплатой, где упоминается банк»:

```
/vacancies?is_new=true&has_salary=true&search=банк
```

**`/fetches` без фильтров** — ✅ согласен: выгрузок около десятка, фильтровать нечего.

### Что получилось

| URI | Что возвращает |
|---|---|
| `/vacancies` | Вакансии, вошедшие в анализ (без повторов, AC 6.5) |
| `/vacancies?is_new=…&has_cover_letter=…&has_salary=…&search=…` | Та же коллекция с условиями |
| `/vacancies/{id}` | Одна вакансия — данные для карточки |
| `/fetches` | Список выгрузок |
| `/fetches/{id}` | Одна выгрузка |

### Вопросы на потом

- ~~На кнопках фильтров видны счётчики (Все 59, Новые 7…). Откуда интерфейсу их взять — посчитать самому по всему списку или получить от API?~~ — **решено**, см. ниже.
- Сортировку по дате на экране не делают, но в API её часто закладывают сразу: `sort=-published_at`.

### Решение: счётчики на кнопках фильтров считает API

Предложение пользователя — счётчики считает API, интерфейс показывает готовые числа. **Принято.**

Почему на сервере:

1. **AC 6.2** — интерфейс не дублирует логику CLI. Правила «новая вакансия» (по выгрузкам) и «есть письмо» (по файлам `reports/`) знает Python-код; посчитай их браузер — правило окажется в двух местах и со временем разойдётся.
2. **Пагинация** — при выдаче страницами браузер видит только текущую страницу и правильно посчитать не может.
3. **Проще интерфейс** — он только показывает числа.

Считать в браузере допустимо, когда список маленький, приходит целиком и признаки уже есть в каждом элементе. У нас 87 вакансий — сработало бы, но п. 1 перевешивает.

Как передают — вместе со списком, блоком метаданных (*facets*), а не отдельным запросом:

```json
{
  "items": [ { "id": "137828745", "name": "…", "is_new": true } ],
  "total": 87,
  "counts": { "new": 7, "has_cover_letter": 3, "has_salary": 21 }
}
```

### Решение: счётчики учитывают строку поиска

Вопрос: при поиске «банк» «Новые 7» превращается в «Новые 2» или остаётся 7? **Решено — учитывают** (лучшая практика *faceted search*, числа на фильтрах — *contextual counts*).

**Правило: число на кнопке = сколько строк увидишь, если её нажмёшь.** Иначе ожидание обманывается: «Новые 7» → нажал → 2 строки, кажется, что данные пропали (исследования фильтров Nielsen Norman Group, Baymard Institute).

Сопутствующие практики:

1. **Итог рядом с поиском** — «Найдено 12 из 87»: и результат, и полный объём.
2. **Нули показываем, кнопку не прячем** — «С письмом 0» тоже информация; кнопку можно сделать неактивной. Исчезающие кнопки сдвигают раскладку.
3. **Фильтры одной группы не перемножаются** — кнопки работают как вкладки (выбрана одна), поэтому счётчик каждой = «поиск + своё условие», независимо от выбранной сейчас кнопки.
4. **Пересчёт с паузой** — после последней клавиши ~300 мс (*debounce*), чтобы не запрашивать сервер на каждую букву.

**Для API:** `/vacancies?search=банк` возвращает `counts` уже с учётом поиска; каждый счётчик — «поиск + своё условие». Структуру ответа подробно — отдельным понятием.

**Для прототипа:** сейчас счётчики считаются по всему списку без учёта поиска и нет строки «Найдено N из M» — доработка внесена в бэклог, п. 30.
